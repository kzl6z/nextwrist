# 04 — V0.1 : le plan des 30 jours

## Objectif et périmètre

**Objectif :** un assistant local, privé, qui te connaît un peu et qui a lu tes
documents. Utilisé tous les jours.

| Dans la V0.1 | Hors V0.1 (résiste à la tentation) |
|---|---|
| LibreChat + Ollama en local | ❌ Voix |
| Un modèle Qwen 3 adapté à ta machine | ❌ Caméra / vision |
| Postgres + pgvector | ❌ Recherche web |
| Ingestion de documents (RAG natif LibreChat) | ❌ Serveurs MCP |
| Prompt système « Nova » versionné | ❌ Mémoire automatique |
| Fichier `facts.md` en mémoire manuelle | ❌ Accès distant |
| Sauvegarde automatique + **restauration testée** | ❌ Multi-utilisateurs |

La colonne de droite n'est pas une frustration : c'est ce qui rend les 30 jours
tenables. Chaque élément y a sa version dédiée dans la feuille de route.

## Semaine 1 — Le socle tourne

**Livrable : tu discutes avec un modèle local dans ton navigateur.**

| Jour | Tâche | Fait quand |
|---|---|---|
| J1 | Docker installé, `hello-world` OK. Répertoire `nova/` créé, dépôt git initialisé. | `docker ps` répond |
| J2 | Ollama installé, un petit modèle testé (`qwen3:4b`) en ligne de commande. | Il répond en français |
| J3 | Identifier ta VRAM/RAM réelle, choisir ta ligne dans le tableau matériel, télécharger LE modèle. | `ollama run` fluide |
| J4-J5 | LibreChat via `docker compose` (**version épinglée**). Il démarre, tu crées ton compte. | Page de connexion accessible |
| J6 | Connecter LibreChat → Ollama (`librechat.yaml`, endpoint personnalisé). | Ton modèle apparaît dans la liste |
| J7 | Premier vrai échange. Mesurer la vitesse. Ajuster la taille du modèle si c'est pénible. | 🎉 Tu discutes en local |

> **Piège classique de la semaine 1 :** depuis un conteneur, `localhost` désigne le
> conteneur lui-même, pas ta machine. Pour joindre Ollama depuis LibreChat, c'est
> `host.docker.internal` (Mac/Windows) ou l'IP de la passerelle Docker (Linux). Si
> quelque chose refuse de se connecter cette semaine, c'est probablement ça.

## Semaine 2 — Nova a une identité

**Livrable : ce n'est plus « un modèle », c'est Nova.**

| Jour | Tâche |
|---|---|
| J8-J9 | Écrire `config/prompts/nova-system.md` : qui est Nova, comment elle parle, ce qu'elle ne fait pas. Versionné dans git — c'est un actif du projet, il évoluera 50 fois. |
| J10 | Créer un « agent » Nova dans LibreChat avec ce prompt. |
| J11 | Écrire `facts.md` : 20-30 faits sur toi (contexte, projets en cours, préférences de travail, ce que tu détestes qu'on te réponde). L'ajouter au prompt. |
| J12 | Régler les paramètres : température, longueur de contexte. Tester la même question à 0.2 et 0.8, choisir. |
| J13-J14 | **Tester 3 modèles sur 10 de tes vraies questions.** Noter les résultats dans un fichier. Trancher. |

### Ce qui fait un bon prompt système

Le réflexe est d'écrire « Tu es Nova, un assistant utile et bienveillant » — c'est
inutile, tous les modèles font déjà ça. Ce qui change réellement le comportement :

- **Des interdictions précises** : « ne reformule jamais ma question avant de
  répondre », « n'ajoute pas de conclusion qui résume ce que tu viens de dire »
- **Une règle d'incertitude** : « si tu ne sais pas, dis-le en une phrase et propose
  ce qu'il faudrait pour savoir » — c'est la règle la plus rentable de toutes
- **Le contexte du destinataire** : ton niveau, tes projets, ton domaine
- **Le format attendu** : longueur par défaut, quand utiliser des listes, quand ne
  pas en utiliser

Tu retoucheras ce fichier chaque semaine pendant un an. C'est normal. C'est le
principal levier de personnalisation de Nova — bien avant le choix du modèle.

## Semaine 3 — Nova lit tes documents

**Livrable : Nova répond sur tes propres documents.**

| Jour | Tâche |
|---|---|
| J15 | Activer Postgres + pgvector et le service RAG de LibreChat. |
| J16 | Configurer les embeddings sur **`bge-m3` via Ollama** (pas un modèle anglophone). |
| J17 | Ingérer 5 documents variés : un PDF texte, un PDF scanné, un DOCX, un Markdown, une page web enregistrée. |
| J18 | Tester 10 questions dont tu connais les réponses. Noter les échecs. |
| J19 | Corriger : taille des morceaux, recouvrement, nombre d'extraits remontés. |
| J20 | Ingérer un corpus réel (20-50 documents). |
| J21 | Re-tester. **Vérifier les citations.** |

### Diagnostic si le RAG répond mal

Le symptôme « Nova ne trouve pas » a presque toujours l'une de ces 4 causes, dans cet
ordre de fréquence :

1. **Mauvais modèle d'embeddings** (anglophone sur du français) → cause n°1, de loin
2. **Morceaux trop gros** (le signal utile est noyé) ou **trop petits** (le contexte
   est perdu). Point de départ raisonnable : 800-1200 tokens, 15 % de recouvrement.
3. **Extraction du PDF ratée** — vérifie *ce qui a réellement été extrait* avant
   d'accuser le modèle. Un PDF scanné sans OCR donne du vide.
4. **Trop peu d'extraits remontés** (essaie 5-8 plutôt que 3)

Change **une seule chose à la fois** et re-teste sur le même jeu de 10 questions.
C'est fastidieux et c'est la seule méthode qui marche.

## Semaine 4 — Nova est fiable

**Livrable : un système que tu peux utiliser sans crainte de tout perdre.**

| Jour | Tâche |
|---|---|
| J22 | Script de sauvegarde (`data/postgres` + `data/documents`) via restic. |
| J23 | **Restaurer la sauvegarde dans un dossier vide et vérifier que tout est là.** Une sauvegarde non testée n'existe pas. |
| J24 | Sauvegarde automatique quotidienne (cron / tâche planifiée). |
| J25 | `docker compose` avec redémarrage automatique. Vérifier : Nova revient seule après un reboot. |
| J26 | Documenter dans un `RUNBOOK.md` : comment démarrer, arrêter, mettre à jour, restaurer, où sont les logs. Tu ne t'en souviendras pas dans 3 mois. |
| J27 | Tout committer dans git (**sans** les données ni le `.env`). |
| J28-J30 | **Utilisation réelle uniquement.** Aucune nouvelle fonctionnalité. Noter les irritants dans `BACKLOG.md`. |

Les trois derniers jours sans développement sont volontaires et sont la partie la
plus importante du mois : c'est en utilisant qu'on découvre ce qui manque vraiment,
et ça donne le contenu de la V0.2 — à partir de ton usage réel, pas de tes
suppositions.

## Critères de réussite de la V0.1

- [ ] Nova démarre seule après un redémarrage de la machine
- [ ] Réponse en moins de 10 secondes sur une question simple
- [ ] Elle répond correctement sur au moins 8 questions sur 10 portant sur tes documents
- [ ] Elle cite ses sources
- [ ] Elle dit « je ne sais pas » quand c'est le cas
- [ ] Sauvegarde automatique **et restauration vérifiée au moins une fois**
- [ ] Tu l'as utilisée 5 jours d'affilée par préférence
- [ ] Aucune donnée personnelle n'est sortie de ta machine

## Les 5 façons d'échouer (par ordre de fréquence)

1. **Vouloir la voix dès le premier mois.** C'est la tentation n°1. La voix sur une
   base instable donne un système inutilisable et décourageant. V0.5, pas avant.
2. **Prendre un modèle trop gros pour la machine.** 2 tokens/s, tu abandonnes en 10
   jours. Prends plus petit que ce que tu crois pouvoir faire tourner : un modèle
   rapide et moyen bat un modèle excellent et inutilisable.
3. **Ne pas mettre en place les sauvegardes.** Tu perds 3 mois de mémoire, tu ne
   recommences pas.
4. **Utiliser `:latest` partout.** Une mise à jour casse la config un mardi soir, tu
   ne sais pas quoi a changé, tu perds une semaine.
5. **Construire sans utiliser.** Si tu ne t'en sers pas quotidiennement dès la V0.1,
   tu construis pour un utilisateur imaginaire.
